# 存储方案：双层缓存与断点续答

## 一、核心架构与设计目标概述

- **存储方案核心主题**  
    - 双层缓存与断点续答机制  
    - 面向高交互、长周期场景的可靠性与性能平衡设计  

- **背景与核心挑战**  
    - 面试过程属于**长耗时、高频交互**的应用场景  
        - 用户持续输入、系统频繁响应，产生大量中间状态数据  
        - 对响应延迟敏感，需保障操作流畅性  
    - 数据持久化与访问速度之间存在天然矛盾  
        - 直接读写数据库（DB）响应慢，影响用户体验  
        - 完全依赖缓存则存在数据丢失风险  

- **整体设计目标**  
    - 实现**热冷分离的存储策略**  
        - 热数据：高频访问的中间状态 → 存于内存（Redis）以提升响应速度  
        - 冷数据：关键状态变更与最终结果 → 持久化至数据库（PostgreSQL）保障可靠性  
    - 在**响应速度**与**数据可靠性**之间取得最优权衡  
        - 用户无感知的故障恢复能力  
        - 支持异常中断后的会话无缝衔接  

- **关键机制预览**  
    - 采用 **Write-Through with Degradation** 写入策略  
        - 优先写入 Redis 实现快速响应  
        - 异步尝试落盘 DB，失败时不阻塞主流程  
    - 构建完整的**故障降级与恢复体系**  
        - 包括 Redis 宕机、缓存丢失、数据不一致等典型场景应对方案  
    - 实现**断点续答（Session Resume）功能**  
        - 用户异常退出后可从上次进度恢复答题体验

## 二、系统组件与运行机制详述

- **系统架构组件**
    - **客户端**
        - 用户：作为面试流程的发起方，进行题目作答与交互操作
    - **后端应用**
        - Interview Service：核心业务服务模块，负责接收用户请求、协调AI推理与数据存储逻辑
    - **AI 层**
        - Spring AI：集成框架，用于封装和调用大语言模型能力
        - 大语言模型：提供智能问答生成、语义理解等核心AI功能
            - 与 Spring AI 存在双向交互机制，支持动态反馈与上下文保持
    - **存储层**
        - Redis 热缓存：存放高频访问的中间状态数据，实现低延迟读写（p99 < 10ms）
        - PostgreSQL 持久化：作为最终落盘的数据源，保障关键数据的可靠性与持久性
            - 支持异步保存路径，在非关键操作中延迟写入以提升整体性能
    - **数据流向**
        - 用户 → Interview Service（请求入口，触发后续处理链路）
        - Interview Service → AI 层（发起智能推理请求，获取AI生成结果）
        - Interview Service ↔ Redis 热缓存（实时读写当前会话状态，如答案暂存与索引更新）
        - Interview Service → PostgreSQL 持久化（通过异步机制完成关键状态归档）

- **Redis 热缓存机制**
    - **暂存内容**
        - 已填写的答案：用户在面试过程中提交的每道题回答内容
        - 当前索引（currentIndex）：记录用户当前所处题目位置，支持进度追踪与恢复
    - **序列化方式**
        - 使用 **Redisson** 将会话对象（CachedSession）序列化为 JSON 格式存储
            - 保证对象结构完整可还原，便于跨服务共享与调试分析
    - **性能表现**
        - 题目切换与答案暂存均在内存中完成，无磁盘IO开销
        - 在本地网络环境下，p99 延迟约 **< 10ms**
            - 测试环境基于 Redis 单机部署，未启用集群分片

- **存储策略与一致性权衡**
    - 采用 **Write-Through with Degradation** 写入策略
        - 适用场景：状态发生关键变更时（如会话初始化、交卷提交）
    - **当前实现步骤**
        - a. 数据优先写入 Redis（快速响应用户操作，降低感知延迟）
        - b. 同步尝试写入 PostgreSQL（尽力而为模式，不强制等待成功）
        - c. DB 写入失败时仅记录 WARN 日志，不阻塞主流程
            - 确保高可用性优先于强一致性，保障用户体验连续性

- **故障处理机制**
    - **Redis 写入失败**
        - 操作失败，立即返回错误给用户
        - 触发前端重试或提示机制，引导用户重新操作
    - **DB 写入失败**
        - 记录 WARN 级别日志，用于后续监控告警与问题追溯
        - 主流程继续执行，用户无感知
    - **Redis 宕机**
        - 系统自动降级为直连 DB 模式
        - 响应延迟增加至 **50–100ms**
        - 待 Redis 恢复后逐步重建缓存
    - **缓存数据丢失**
        - 从 DB 全量重建 Redis 缓存
        - 过程对用户透明，无感知影响
    - **DB 与 Redis 不一致**
        - 以 **DB 为准**，因其为持久化真相源
        - 可通过定时校验任务修复长期不一致状态

- **断点续答（Session Resume）**
    - **设计目标**
        - 确保用户中途异常退出后，下次进入可恢复会话
        - 实现答题进度的无缝衔接，提升用户体验连续性
    - **恢复流程**
        1. 用户再次进入时，系统从 PostgreSQL 查询 `IN_PROGRESS` 或 `COMPLETED` 状态的会话
        2. 比对 Redis 缓存是否存在该会话
            - 若不存在，则从 DB 反序列化重建至 Redis
        3. 恢复至最后一题的索引位置（currentIndex），用户可继续答题
